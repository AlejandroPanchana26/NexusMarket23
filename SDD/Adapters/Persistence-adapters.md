# Persistence Adapters

## 1. Overview

Persistence adapters implement the output ports of the domain. The domain only knows the ports (for example `OrderRepositoryPort`); the adapters decide how the data is stored.

NexusMarket uses two databases:

| Database | Technology | Stores |
| -------- | ---------- | ------ |
| MySQL 8 | Spring Data JPA (Hibernate) | All business data: persons, users, warehouses, products, inventory, carts, orders, invoices, shipments, returns and refunds |
| MongoDB 6 | Spring Data MongoDB | The inventory movement history (`inventory_movements`), which is only appended and never modified |

The inventory movement history goes to MongoDB because it is the equivalent of an audit trail: every entry, reservation, sale exit, adjustment and return, with who performed it and when. This covers the traceability goal of the functional specification without changing the domain, because `InventoryMovementRepositoryPort` already existed.

---

## 2. Structure Pattern

Each stored entity uses four pieces:

| Piece | Location | Responsibility |
| ----- | -------- | -------------- |
| JPA entity | `adapters/persistence/jpa/entities` | Represents a table. Only simple columns, annotated with `@Entity`, `@Table` and `@Column`. |
| Spring Data repository | `adapters/persistence/jpa/repositories` | Interface that extends `JpaRepository`. Spring implements it and builds the queries from the method names (for example `findByBuyerIdentification`). |
| Mapper | `adapters/persistence/jpa/mappers` | Converts domain model → entity (`toEntity`) and entity → domain model (`toDomain`). |
| Adapter | `adapters/persistence/jpa` | Implements the output port with `@Repository`, using the three pieces above. |

MongoDB follows the same pattern in `adapters/persistence/mongodb` (`documents`, `repositories`, `mappers` and the adapter).

```text
Domain service ──uses──> OutputPort <──implements── JpaAdapter ──uses──> Mapper + SpringDataRepository ──> MySQL
```

## 3. Mapping Rules

* **Catalogs are stored as text.** A value object such as `OrderStatus.PAID` is stored as its code (`"PAID"`). `CatalogMapper` converts in both directions (`toCode` and one method per catalog, such as `orderStatus("PAID")`).
* **Relations are stored as identifiers.** A table stores the identifier of the related entity (for example `buyer_identification`). When reading, the adapter rebuilds the related domain object through the corresponding output port (for example, `OrderJpaAdapter` uses `PersonRepositoryPort` to rebuild the buyer). Adapters reuse other ports instead of duplicating code.
* **One table per hierarchy.** Buyers, sellers and employees share the table `persons` (column `person_type`). Physical and digital products share the table `products` (column `product_type`; `weight` is only filled for physical products and `download_url` only for digital products).
* **Lists in auxiliary tables.** Lists use `@ElementCollection` with `FetchType.EAGER`: simple lists (addresses, variants) and lists of `@Embeddable` lines (cart items and order details), which have no identity of their own.
* **Stored values are preserved.** When rebuilding cart items, order details and inventory movements, the mappers use the empty constructors and set the stored values. The constructors with parameters would take the current product price or the current date, breaking the frozen price rule and the movement history.
* **Generated identifiers.** Users use an auto-increment `user_id` generated by MySQL; the adapter copies it back to the domain object. The other entities use the UUID assigned by the domain services.

## 4. Database Rules That Reinforce the Domain

The domain services already validate these rules; the database protects them a second time:

| Rule | Database Constraint |
| ---- | ------------------- |
| Email, username and buyer cart are unique | `UNIQUE` on `persons.email`, `users.username`, `shopping_carts.buyer_identification` |
| One inventory record per product and warehouse | Composite `UNIQUE` on `inventories (product_identifier, warehouse_identifier)` |
| One shipment per order | `UNIQUE` on `shipments.order_identifier` |
| One refund per return | `UNIQUE` on `refunds.return_identifier` |

## 6. MongoDB Collection

### `inventory_movements` — `InventoryMovementDocument`

| Field | Type | Description |
| ----- | ---- | ----------- |
| `_id` | String | Movement identifier |
| `inventoryIdentifier` | String | Inventory record of the movement |
| `productIdentifier` | String | Product moved (stored so that the document is self-explanatory) |
| `warehouseIdentifier` | String | Warehouse where the movement happened |
| `movementType` | String | `ENTRY`, `RESERVATION`, `SALE_EXIT`, `ADJUSTMENT` or `RETURN` |
| `quantity` | Integer | Units moved (for `ADJUSTMENT`, the new available quantity) |
| `date` | Date | When the movement happened |
| `performedByUsername` | String | User who performed the movement |
